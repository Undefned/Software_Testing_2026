# Подготовка к защите ЛР №4 — нагрузочное и стресс-тестирование

---

## Часть 1. Восстановленные вопросы с пары (по твоим "рваным" заметкам)

### 0. Важное замечание препода (не вопрос, а требование к лабе)

> «При стресс-тестировании ловим 503, а не останавливаемся по достижении максимального времени отклика. 500 не равно 503!»

**Что это значит.** У тебя в стресс-тесте два разных критерия отказа, и их нельзя путать:

- **Duration Assertion (время отклика > лимита)** — это нарушение SLA, но само по себе ещё не значит, что сервер "лёг". Он мог просто подтормаживать под нагрузкой.
- **HTTP 503 Service Unavailable** — это явный сигнал от сервера: "я физически не могу обработать запрос, ёмкость исчерпана". Это и есть настоящая точка отказа по производительности.
- **HTTP 500 Internal Server Error** — это вообще про другое: необработанное исключение/баг в коде. Может вылезти и без всякой перегрузки. **500 ≠ 503**, в отчёте их нельзя валить в одну кучу "ошибки".

Вывод для лабы: в стресс-тестировании (особенно во втором эксперименте, где мы "кладём сервер") главная метрика — **первое появление именно кода 503**, а не просто момент, когда среднее время отклика ушло за 600мс. Именно поэтому в твоём `Stress test.jmx` Duration Assertion в Exp2 отключён — чтобы не путать SLA-нарушения с реальным падением сервера, и ошибки считаются по типам (500 / 503 / нет ответа) отдельно.

### 1. Как определяется ожидаемая нагрузка на систему? Кто её считает?

Нагрузку не берут "с потолка" — её выводят из анализа **целевой аудитории** и бизнес-профиля использования: сколько одновременных пользователей ожидается в обычное время и в пиках, какой прогноз роста, какие сценарии использования самые частые. Обычно это фиксируется документом с **нефункциональными требованиями (NFR/SRS)** — то же самое, на что ссылается слайд про приёмочное тестирование ("источник — документ «требования к системе»").

Определяет это чаще всего **заказчик/бизнес** совместно с аналитиками и архитекторами, а заказчик же и обеспечивает под эту нагрузку ресурсы (бюджет на инфраструктуру). В нашей лабе это прямо задано вариантом: "10 пользователей × 40 запр/мин" — это и есть тот самый заранее определённый профиль нагрузки, который в реальном проекте вывели бы из анализа аудитории.

### 2. Зачем нам знать пропускную способность (throughput) сервиса?

- **Масштабирование** — понимать, когда и насколько нужно добавить ресурсов (инстансы, CPU/RAM), пока не начались реальные проблемы у пользователей.
- **Сокращение ресурсов / экономия** — если реальная нагрузка сильно ниже запаса прочности, дорогую конфигурацию можно не покупать (это буквально то, что ты и делаешь в ЛР — ищешь самую дешёвую подходящую конфигурацию).
- **SLA перед бизнесом/клиентами** — нельзя обещать то, что система не может выдержать.
- **Capacity planning** — планирование роста инфраструктуры заранее, с запасом под будущую нагрузку.

### 3. Какие проблемы возникают при восстановлении системы после сбоя? (контекст MTTR)

- **Thundering herd / retry storm** — все запросы, которые копились в очереди или ретраились клиентами во время сбоя, одновременно обрушиваются на только что поднявшийся сервер и кладут его повторно.
- **Холодный старт** — пустые кэши, разорванные пулы соединений к БД, непрогретая JVM/JIT — первые запросы после рестарта аномально медленные.
- **Потеря/рассогласование состояния** — если сбой произошёл посреди операции, могут остаться незавершённые или противоречивые данные.
- **Каскадные отказы** — зависимые сервисы могли упасть вместе с этим, поднять один компонент не значит поднять всю цепочку.
- **Health-check flapping** — балансировщик может начать слать трафик на сервис, который формально "жив", но ещё не до конца прогрелся.

### 4. Зачем нам знать, что конкретно упало (один сервис упал, а другой нет)?

Чтобы **локализовать узкое место (bottleneck)** и оптимизировать/масштабировать именно тот компонент, который реально ограничивает производительность — вместо того чтобы вслепую и дорого наращивать ресурсы всей системы целиком. Это и есть ответ на "что нужно оптимизировать" — точечное решение вместо расточительного.

### 5. Capacity testing? Accuracy? Observability? В чём всё измеряется?

Это фактически расшифровка **CARAT** (см. билет 3 ниже) плюс смежный термин:

- **Capacity testing (тестирование ёмкости)** — поиск максимальной нагрузки, которую система выдерживает, всё ещё соответствуя требованиям.
- **Accuracy (точность)** — корректность ответов под нагрузкой: система должна не просто быстро отвечать, а отвечать *правильно* (не отдавать битые/усечённые данные из-за перегрузки).
- **Observability (наблюдаемость)** — возможность понять внутреннее состояние системы по внешним сигналам (метрики, логи, трейсы). Именно observability даёт ответ на вопрос №4 — "что конкретно упало".

**Единицы измерения:**

| Метрика | В чём измеряется |
|---|---|
| Response time | мс / сек |
| Throughput | запросов в секунду или в минуту (RPS / RPM) |
| Availability | % аптайма ("пять девяток" — 99.999%) или через MTBF/MTTR в единицах времени |
| Capacity | кол-во одновременных пользователей / транзакций |
| Error rate | % от общего числа запросов |

### 6. Какие вообще бывают тестирования? (общая таксономия)

- **По уровню:** Unit → Integration → System → Acceptance.
- **По подходу:** функциональное (работает ли как задумано) vs нефункциональное (производительность, надёжность, безопасность, совместимость, юзабилити).
- **Внутри нефункционального:** performance (load/stress/volume/spike/soak/capacity), стабильность, отказоустойчивость, совместимость.
- **По степени формальности/исполнителю:** Alpha (внутри компании-разработчика) → Beta (реальные внешние пользователи) → Acceptance (заказчик).

## Часть 2. Официальные вопросы к защите (из методички)

### 1. Тестирование системы целиком — системное тестирование

Тестирование полностью интегрированной системы на соответствие заявленным требованиям (функциональным и нефункциональным). Выполняется после интеграционного тестирования, обычно по принципу «чёрного ящика», часто независимой командой тестировщиков. Включает в себя множество видов: функциональное, тестирование производительности, безопасности, совместимости, надёжности и т.д.

### 2. Тестирование возможностей, стабильности, отказоустойчивости, совместимости

- **Возможностей (capability)** — проверка, что все заявленные функции реально работают как специфицировано.
- **Стабильности** — длительное непрерывное тестирование (soak), проверка, что система не деградирует со временем (утечки памяти, исчерпание ресурсов).
- **Отказоустойчивости** — способность системы продолжать работу или корректно восстанавливаться при сбоях (аппаратных, сетевых, падении сервиса) — напрямую связано со слайдом про MTBF/MTTR/готовность.
- **Совместимости** — работа системы в разных окружениях: ОС, браузеры, версии зависимостей, взаимодействие с другими системами.

### 3. Тестирование производительности — CARAT

> ⚠️ Это акроним конкретно из вашего курса, я не нашёл его как общепринятый индустриальный термин — восстанавливаю по слайдам (время отклика / готовность / пропускная способность буквально совпадают с 3 из 5 букв) и по твоим заметкам ("capacity", "accuracy" в списке вопросов). Сверь с конспектом/презентацией лектора, если есть возможность — на всякий случай.

Пять аспектов производительности:
- **C — Capacity** (ёмкость / максимальная нагрузка)
- **A — Availability** (готовность, MTBF/MTTR/MTTF)
- **R — Reliability / Response time** (надёжность / время отклика)
- **A — Accuracy** (точность ответов под нагрузкой)
- **T — Throughput** (пропускная способность)

### 4. Альфа и Бета тестирование. Приёмочное тестирование

**Alpha-тестирование** — проводится небольшим числом пользователей *внутри организации-разработчика*, может идти ещё до завершения системного тестирования, даёт ранние отзывы об использовании системы в рабочем окружении.

**Beta-тестирование** — проводится выбранной группой *внешних* пользователей в их собственном окружении (пример со слайда — Windows Beta test по всему миру). Могут быть баги, может быть нереализован весь функционал. Даёт ранние отзывы разработчикам и превью для пользователей.

Общее для обоих: проводятся **неформально** — пользователи работают с тем функционалом, который им интересен, отмечают что не работает, доводят дефекты до разработчика. Нет формальных тест-кейсов и планов. Разработчики не гарантируют немедленного исправления — фикс может попасть либо в финальный релиз, либо в следующую бета-версию.

**Приёмочное тестирование (Acceptance testing)** — ключевое отличие: управляется **пользователями/заказчиком**, а не разработчиками. Проверяет систему на «соответствие предназначению и практическому использованию» — все ли функциональные и нефункциональные требования удовлетворены. Источник требований — документ «требования к системе» (SRS, часть RUP). Может быть формальным и неформальным; подготовка может начинаться на ранних этапах разработки, может применяться статическое тестирование (ревью требований). Перед началом окружение (аппаратное и программное) должно быть полностью готово — иногда это первый запуск в реальном рабочем окружении. Важно ответственно подойти к выбору пользователей-тестировщиков и обязательно их обучить.

### 5. Нагрузочное тестирование — виды, цели и решаемые задачи

**Виды:**
- **Load testing** — проверка на заданной/ожидаемой нагрузке (соответствует ли система SLA).
- **Stress testing** — постепенное увеличение нагрузки до отказа, поиск предела.
- **Volume testing** — тестирование большими объёмами данных.
- **Spike testing** — резкие скачки нагрузки (вверх и вниз).
- **Soak/endurance testing** — длительная нагрузка для выявления деградации со временем.
- **Capacity testing** — определение максимального числа пользователей/транзакций при сохранении соответствия требованиям.

**Цели и задачи:** проверить, что SLA соблюдается при ожидаемой нагрузке; найти узкие места; определить максимальную ёмкость системы; обосновать выбор/размер инфраструктуры; дать данные для планирования масштабирования и оптимизации затрат.

### 6. Принципы реализации нагрузочного тестирования ПО

- Профиль нагрузки строится на основе реального/ожидаемого использования (анализ аудитории, бизнес-требования) — см. вопрос 1 из части 1.
- Тестовое окружение максимально приближено к продакшену.
- Нагрузка наращивается постепенно (ramp-up), а не «взрывом».
- Тестирование автоматизировано и воспроизводимо: эмуляция виртуальных пользователей, параметризация (разные токены/юзеры), корректная обработка динамических значений.
- Заранее определены чёткие критерии прохождения/провала (SLA: макс. время отклика, доля ошибок, throughput).
- Мониторится не только клиентская сторона (время отклика), но и серверная (CPU/RAM/диск/сеть).
- Тесты повторяются для снижения шума в измерениях.
- Результаты анализируются с привязкой к конкретному узкому месту/компоненту.

### 7. Инструменты для реализации нагрузочного тестирования

HP LoadRunner, LoadComplete, IBM Rational Performance Tester, LoadUI Pro — коммерческие; Apache JMeter, The Grinder, Tsung — открытые (open-source).

### 8. Apache JMeter — архитектура, поддерживаемые протоколы, особенности конфигурации

**Общее:** бесплатный, кроссплатформенный (Java), простой GUI со встроенными графиками, возможность разработки собственных плагинов, тест-планы хранятся в XML — удобно версионировать (git).

**JMeter — не браузер!** Он не рендерит HTML/CSS, не исполняет клиентский JS — измеряет именно серверное время ответа, а не полное время загрузки страницы глазами пользователя. Путь использования: запись через рекордер → функциональное тестирование (проверка корректности сценария) → нагрузочное тестирование (тот же сценарий, но с нагрузкой).

**Структура тест-плана (порядок выполнения элементов внутри одной области видимости):**
Configuration Elements → Pre-Processors → Timers → Samplers → Post-Processors → Assertions → Listeners.

- **Thread Group** — описывает пул пользователей для теста (количество, ramp-up, loop count и т.д.).
- **Samplers** — формируют запросы и генерируют результаты; поддерживается много протоколов: **TCP, HTTP, FTP, JDBC, SOAP, JMS, SMTP** и др.
- **Logic Controllers** — определяют порядок вызова семплеров, конструкции управления (if, loop), управление потоком выполнения.
- **Timers** — задержки между запросами: постоянные либо по определённым распределениям/законам; Constant Throughput Timer держит целевой RPS.
- **Assertions** — проверяют результаты (код ответа, время выполнения, содержимое и т.д.).
- **Configuration Elements** — хранят предустановленные значения для семплеров (напр. HTTP Request Defaults).
- **Pre-Processors** — изменяют семплеры в их контексте перед выполнением.
- **Post-Processors** — применяются ко всем семплерам в одном контексте после выполнения (например, извлечение данных из ответа).
- **Listeners** — получают ответы, выполняют доп. операции (просмотр/запись/чтение результатов). **Не обрабатывают данные сами** — в headless-режиме (командная строка) для просмотра нужен отдельный GUI-анализ результатов, "на лету" в CLI они не визуализируются.

**Распределённое тестирование:** генератор нагрузки (клиент JMeter) + агенты JMeter дублируют нагрузку на сервер под тестом; на сервере — serverAgent для сбора метрик через PerfMon Metrics Collector Listener; итог — снятие показателей и с клиентской, и с серверной стороны.

**Доп. возможности:** автоматическая генерация CSV с результатами; Bandwidth Throttling — ограничение полосы (статическое по CPS или динамическое по error rate); IP Spoofing — подмена src_ip для разделения клиентов, полезно для проверки балансировщиков нагрузки; поддержка стандартного теста TPC-C (эталонный тест на OLTP-нагрузку).

### 9. Стресс-тестирование — основные понятия, виды стресс-сценариев

**Понятие:** целенаправленное превышение нормальной/ожидаемой ёмкости системы, чтобы увидеть, как именно она откажет, и найти точку отказа.

**Сценарии:**
- **Постепенный рост (ramp stress)** — плавное увеличение нагрузки до отказа (как твой Эксперимент 1 — по одному пользователю в секунду).
- **Резкий скачок (spike stress)** — внезапная массовая нагрузка (как Эксперимент 2 — 300 пользователей за 60 секунд), проверка способности пережить всплеск.
- **Длительная нагрузка под стрессом (soak под стрессом)** — продолжительная высокая нагрузка, проверка деградации/утечек со временем.
- **Истощение ресурсов** — искусственное ограничение CPU/памяти/сети/диска у системы, наблюдение за деградацией.
- **Recovery testing** — после отказа под стрессом проверяется, как система восстанавливается при снижении нагрузки (связано с вопросом 3 части 1).

### 10. Стресс-тестирование ПО. Виды стресс-тестов ПО. Тестирование ёмкости

Виды — по сути пересечение с вопросом 9 (application-level, system-level, транзакционный, распределённый стресс-тест).

**Тестирование ёмкости (capacity testing)** — определяет максимальную нагрузку (число пользователей/транзакций), которую система выдерживает, *продолжая корректно работать и соответствовать SLA*. Отличие от стресс-теста по цели: стресс-тест намеренно ломает систему, чтобы увидеть режим отказа; capacity testing ищет устойчивый максимум, не обязательно доводя систему до явного падения. Используется для ответа на вопрос «сколько реальных пользователей мы можем обслуживать» и для планирования инфраструктуры.

## Часть 3. Глоссарий терминов со слайдов

| Термин | Значение |
|---|---|
| **Response time (время отклика)** | Время от отправки запроса до получения ответа. Один из самых часто измеряемых и критичных показателей, особенно для систем реального времени. Измеряется под минимальной, расчётной и пиковой нагрузкой. |
| **MTBF** (Mean Time Between Failures) | Среднее время между сбоями. |
| **MTTR** (Mean Time To Repair/Recover) | Среднее время восстановления после сбоя. |
| **MTTF** (Mean Time To Failure) | Среднее время до сбоя. |
| **Коэффициент готовности (Availability)** | `(MTBF − MTTR) / MTBF`. Часто выражается как «число девяток» (напр. 99.999%). |
| **Throughput (пропускная способность)** | Количество операций/транзакций в секунду, которое может поддерживать система. Находится в балансе с временем отклика. |
| **Thread Group** | Элемент JMeter, описывающий пул виртуальных пользователей: количество, характер нарастания нагрузки и т.д. |
| **Sampler** | Элемент, формирующий запрос к тестируемой системе и получающий результат. |
| **Listener** | Элемент, получающий и визуализирующий/сохраняющий результаты; сам данные не обрабатывает. |
| **Timer** | Элемент, задающий задержки между запросами. |
| **Assertion** | Элемент, проверяющий корректность результата (код ответа, время, содержимое). |
| **Constant Throughput Timer** | Таймер, удерживающий целевой RPS/RPM независимо от числа потоков. |
| **Duration Assertion** | Проверка, что время ответа не превышает заданный порог. |
| **HTTP 403** | Некорректные параметры запроса (в контексте этой лабы). |
| **HTTP 500** | Внутренняя ошибка сервера (баг/необработанное исключение) — не связана напрямую с перегрузкой. |
| **HTTP 503** | Сервис недоступен — сервер не может обработать запрос из-за перегрузки; главный сигнал отказа в стресс-тесте. |
| **Ramp-up period** | Время, за которое JMeter доводит число активных потоков от 0 до заданного максимума. |
| **Capacity testing** | Поиск максимальной нагрузки при сохранении соответствия требованиям. |
| **Observability** | Возможность понять внутреннее состояние системы по внешним сигналам (метрики/логи/трейсы). |
| **Accuracy** | Точность/корректность ответов системы под нагрузкой. |
